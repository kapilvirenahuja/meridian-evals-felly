## Tech Decisions

| Concern                   | Choice                                                                         | Key Detail                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Guard chain order         | `JwtAuthGuard` first, then `RolesGuard`                                        | JwtAuthGuard sets `request.user`; RolesGuard reads `request.user.realm_access.roles`       |
| Role check                | `RolesGuard` reads `@Roles()` metadata from handler/class                      | If no `@Roles()` → guard passes (any authenticated user)                                   |
| Admin stub endpoint       | `GET /admin/ping` only                                                         | Real admin CRUD is F1.4 scope; stub exists solely to enable RBAC exit-gate test            |
| Frontend middleware token | Non-httpOnly cookie `felly_at` (presence flag)                                 | Next.js Edge Middleware cannot access localStorage; cookie is the only viable mechanism    |
| Frontend middleware role  | Non-httpOnly cookie `felly_role` / `felly_admin_role`                          | Populated after `GET /auth/me` resolves; used by admin portal middleware                   |
| Admin role enforcement    | Backend guards enforce real authorization                                      | Frontend middleware is UX-only (prevents render; not a security boundary)                  |
| Cookie lifetime           | `felly_at`: 900s (matches 15m JWT), `felly_role`: 604800s (matches 7d refresh) | On refresh, a new `felly_at` cookie should be set (handled in `api-client.ts` interceptor) |
| Testing                   | `@nestjs/testing` + `supertest`                                                | Create isolated test app modules; generate test JWTs via MockAuthAdapter directly          |

## Domain Rules

**Guard behaviour:**

- `JwtAuthGuard` (extends `AuthGuard('jwt')`): validates Bearer token via `JwtStrategy`; returns 401 if token missing or invalid; sets `request.user: JwtPayload`
- `RolesGuard`: if `@Roles()` metadata is absent → return `true` (guard passes, any authenticated user allowed); if present, checks `request.user.realm_access.roles` contains required role → 403 if not
- Always apply guards in order `[JwtAuthGuard, RolesGuard]` — never swap; NestJS executes them left-to-right

**RBAC enforcement at API level:**

- `GET /api/v1/users/me` — `@UseGuards(JwtAuthGuard, RolesGuard)`, NO `@Roles()` → any valid JWT passes, 401 if no token
- `GET /api/v1/auth/me` — same: `@UseGuards(JwtAuthGuard, RolesGuard)`, NO `@Roles()` → any valid JWT passes
- `GET /api/v1/admin/*` — `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('ADMIN')` → 401 if no token, 403 if token present but role ≠ ADMIN

**Cookie rule (frontend):**

- `felly_at` cookie is set ONLY when `setTokens()` is called (successful login or token refresh)
- `felly_at` cookie is cleared ONLY when `clearTokens()` is called (logout or auth failure)
- Middleware checks cookie presence, not value — cookie existence signals a valid recent login occurred
- Cookie lifetime intentionally matches JWT expiry; browser auto-expires it even without explicit logout
- After a token refresh (`POST /auth/refresh`), set a fresh `felly_at` cookie in the Axios interceptor in `api-client.ts` (call `setTokens(newAccessToken, newRefreshToken)` with the new tokens)

**Frontend redirect rules (mentee-web-app):**

- `PUBLIC_PATHS = ['/', '/login', '/register', '/verify-email', '/forgot-password', '/reset-password']`
- Any request path starting with a prefix in PUBLIC_PATHS → pass through
- Any other path without `felly_at` cookie → redirect to `/login`
- Do NOT redirect away from `/login` if already authenticated (avoid redirect loops)

**Frontend redirect rules (admin-portal):**

- Public path: `/login` only
- Any non-`/login` path without `felly_admin_role` cookie equal to `ADMIN` → redirect to `/login`
- On login page, if already authenticated as ADMIN, redirect to `/` (dashboard root)

## Do NOT

- **Do NOT** implement F1.4 admin business logic (mentor onboarding, verification) — the AdminModule stub created here has only `GET /admin/ping`
- **Do NOT** implement F1.6 profile endpoints (`GET/PATCH /users/me/mentee-profile`, etc.) — `UserController` created here has only `GET /users/me`
- **Do NOT** use httpOnly cookies — they require backend session management (incompatible with the stateless JWT setup and localStorage pattern already established)
- **Do NOT** use `jose` or any new npm package for JWT parsing in middleware — the middleware only checks cookie presence/value, not JWT validity
- **Do NOT** remove the existing `AUTH_ADAPTER_TOKEN` DI token binding in `auth.module.ts`
- **Do NOT** change the `JwtStrategy` — it already works correctly; do not alter `secretOrKey`
- **Do NOT** add profile fields (`firstName`, `lastName`, `avatarUrl`) to `UserController.getMe()` response — those come from the joined profile; this is F1.6 scope. Return only `{ id, email, role, status }`.
- **Do NOT** call Prisma directly from controllers — always go through service → repository
- **Do NOT** add social login to the admin-portal login-form — admin uses email/password only (already enforced in F1.2)
- **Do NOT** implement password reset endpoints — that is F1.3 scope
